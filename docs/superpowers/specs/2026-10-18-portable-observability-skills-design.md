# Observability Skills for AI Agents: Design

## Goal

Create a collection of five independent, portable observability skills for AI agents, bringing OpenTelemetry guidance into everyday, spec-driven development. The skills must work across OpenCode, Claude Code, and Codex through their native skill discovery mechanisms. The repository will not provide a custom CLI or platform-specific command wrappers.

All repository content, generated examples, and user-facing messages must be in English.

## Scope and distribution

The repository is a portable skill collection. The canonical source layout is `skills/obs-init/SKILL.md`, `skills/obs-guide/SKILL.md`, `skills/obs-audit/SKILL.md`, `skills/obs-impact/SKILL.md`, and `skills/obs-score/SKILL.md`. Each skill is self-contained and has standard `SKILL.md` metadata (`name` and `description`). Shared rules are stated in each skill so it does not depend on loading another skill. The baseline contract is bundled with `obs-init` at `skills/obs-init/references/observability-config.yaml`, so installing that skill alone includes its template. Skill instructions must rely on ordinary repository inspection and file editing tools, not a platform-specific skill API.

The repository will include installation instructions for the native skill directories used by OpenCode, Claude Code, and Codex. Installation copies or links the skill directories into each tool's discovery path. The skills remain the canonical source; installation must not require a build step. Invocation syntax is documented per platform because no universal command syntax exists across the three tools. In particular, `opencode run obs-init` is not promised as a portable command.

## Skill responsibilities

### `obs-init`

Inspect common project manifests such as `package.json`, `go.mod`, and `requirements.txt`, identify the likely service name and technology stack, and create `.observability/config.yaml` from the supplied baseline contract. Do not overwrite an existing contract. Print one concise English status line. Treat uncertain stack detection as unknown instead of guessing.

### `obs-guide`

Read the active SDD feature specification and `.observability/config.yaml`. Return only the observability instructions and focused instrumentation boilerplate relevant to the target code path. Preserve the feature's scope and limit the output to one or two priority actions. Do not introduce high-cardinality metric labels or sensitive data.

### `obs-audit`

Inspect source code and the observability contract for missing instrumentation and guardrail violations. Use code-aware AST inspection when a suitable parser is already available; otherwise use targeted regex/search checks and label the evidence as heuristic. Never treat YAML declarations as proof that instrumentation exists. Print a compact report and create at most one prioritized executable SDD task in `.sdd/observability/` per run, with a second task only when it is independently urgent.

### `obs-impact`

Translate configured SLOs/SLIs and verified critical-path coverage into a three-to-five-line English summary for product stakeholders. Explain customer-visible availability, latency, or error impact. Estimate MTTD, MTTR, or affected-user percentages only when repository evidence provides enough inputs; otherwise state that the value is unavailable.

### `obs-score`

Present a compact text/tree scorecard for logs, metrics, and traces based on source evidence and the contract. Detect critical routes from route handlers or equivalent entry points. Use the same detected routes as the denominator for each pillar; count a route as covered only when source evidence shows a server span for traces, an applicable counter or histogram for metrics, and a structured log with trace context for logs. Report an unknown value when there is no defensible denominator. Keep the output concise and avoid implying runtime coverage from static evidence.

## Shared guardrails

Every skill that discusses or changes instrumentation must enforce these rules:

- Never use dynamic identifiers such as `user_id`, `email`, `account_id`, `order_id`, or `transaction_id` as metric labels. Put such values only in spans or logs when appropriate and sanitized.
- Require asynchronous, non-blocking export and fail-silent behavior so telemetry failures do not alter business behavior. Prefer the OpenTelemetry `BatchSpanProcessor` pattern for traces.
- For asynchronous/event-driven boundaries such as Kafka, RabbitMQ, and SQS, require W3C `traceparent` context propagation through message headers.
- Verify instrumentation in source code with AST or targeted regex/search evidence. A configuration declaration alone is insufficient.
- Do not collect secrets, credentials, raw request bodies, or unnecessary personal data.
- Drip-feed findings: produce no more than one or two prioritized actions in a run.

The baseline contract generated by `obs-init` is defined exactly by `skills/obs-init/references/observability-config.yaml`:

```yaml
version: "1.0"
service: "unnamed-service"
telemetry_standard: "opentelemetry"
maturity_level: "baseline" # baseline | intermediate | advanced

guardrails:
  forbidden_metric_labels:
    - "user_id"
    - "email"
    - "account_id"
    - "order_id"
    - "transaction_id"
    - "session_id"
    - "request_id"
    - "ip_address"
  fail_silent: true
  async_export: true
  event_driven_propagation: true

pillars:
  traces:
    required_in_scopes: true
    sampling_ratio: 1.0
    propagation: "w3c"
    mandatory_attributes:
      - "app.environment"
  metrics:
    framework_defaults: true
    custom_metrics_limit_per_scope: 2
    required_types:
      - "counter"
      - "histogram"
  logs:
    structured: true
    inject_trace_id: true
    min_level: "info"
```

## State and artifact flow

Each audited project owns its state in `.observability/config.yaml`; the skill collection itself does not keep user-project state. `obs-init` creates that contract once. The guide, audit, impact, and score skills read it as input and do not silently rewrite it. `obs-impact` may read optional user-maintained SLO/SLI fields if present; their absence means numerical business impact estimates are unavailable.

Audit findings that require implementation become Markdown tasks in `.sdd/observability/`, with a unique sequential identifier and a descriptive feature slug. Each task states evidence, the required change, and acceptance criteria so it can be executed through SDD. The auditor must avoid duplicate tasks when an equivalent open task already exists.

If the contract or requested SDD specification is missing, a skill reports the single prerequisite needed to continue rather than producing speculative results. Skills should avoid unrelated repository edits.

## Repository deliverables

- Five independent, portable skill directories with standard metadata and focused instructions.
- The baseline observability contract template bundled inside `obs-init`.
- English installation and usage documentation for OpenCode, Claude Code, and Codex.
- A clear README and contribution guidance for the repository. License selection remains an explicit repository-owner decision before publication; no license will be assumed by the implementation.
- A lightweight automated validation suite for package structure, skill metadata, required guardrails, and the baseline YAML template. These checks validate the skill collection; they are not a runtime CLI.

## Validation and acceptance criteria

1. Each of the five skills is discoverable as an independent `SKILL.md` package and contains portable frontmatter (`name` and `description`) plus its own activation and output guidance.
2. Installation documentation names the supported tool discovery paths and explains that invocation syntax is platform-specific.
3. The baseline template parses as YAML and includes all required fields and defaults from the request.
4. Static checks confirm the shared guardrails appear in the relevant skills and that outputs enforce the one-or-two-action limit.
5. The audit instructions distinguish AST evidence from regex heuristics, check implementation in source, and never accept YAML as proof of runtime instrumentation.
6. The impact skill never fabricates SLO, MTTD, MTTR, or affected-user figures; the score skill never fabricates a coverage denominator.
7. All repository documentation and skill text are in English.

## Explicit exclusions

- No custom executable CLI, daemon, API server, package runtime, or telemetry exporter.
- No OpenCode-only command wrappers or assumptions that a skill is invoked with the same command in every host.
- No automatic edits to application source code by `obs-guide` or `obs-audit`; they produce focused guidance and executable SDD artifacts.
- No claims of runtime telemetry coverage based only on static inspection.

## Design review

- Scope is limited to portable skill packages, the `obs-init` template, installation documentation, and package validation.
- The canonical state boundary is the audited repository's `.observability/config.yaml`.
- Static evidence and runtime coverage are explicitly distinguished.
- Invocation is documented per host, with no contradictory promise of a universal command.
- License selection is an explicit owner decision rather than an implementation placeholder.
